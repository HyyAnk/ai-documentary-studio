# CONFIRMED ROOT CAUSES (re-verify line numbers before editing)

| # | Symptom (observed in rendered MP4) | File | Confirmed cause |
|---|---|---|---|
| 1 | The round "?" countdown token on the Thinking Bar visibly squashes into an oval/teardrop as the bar drains, worst near the end of the countdown | `apps/server/src/quiz/render/candyArcadeComposition.ts` — `.timer-progress` (~line 251) and `.timer-marker` (~line 252), HTML in `thinkingBar()` (~line 138) | `.timer-marker` is rendered as a **child** of `.timer-progress`, and `.timer-progress` has `animation: quiz-timer-drain` which does `transform: scaleX(1) → scaleX(0)` (keyframes ~line 326). CSS transforms apply to the whole subtree, so the circular marker (`border-radius:50%`, fixed `width/height:76px`) gets its rendered width compressed by the same non-uniform X-only scale as the fill, distorting the circle. This is a regression introduced by the V3 fix described in `docs/candy-arcade-v3-root-cause.md` under "Progress visual quality" ("coupled transformed progress parent") — that fix correctly solved the countdown-tick jump-cut bug but coupled the marker's shape to the fill's non-uniform scale. |
| 2 | Every question, regardless of which layout the Director/registry selected, renders with the same small image on top and answer rows stacked underneath — image never sits large and full-bleed beside the answers | `apps/server/src/quiz/visual/candyArcade.ts` `resolveLayout()` (~line 74–79) computes `media_left_choices_right` and `media_top_choices_bottom` as real layout IDs, and `candyArcadeComposition.ts` applies them as CSS classes (`layout-${visual.layoutId}`, ~line 92). But grepping the composition's CSS (~lines 197–345) for `.layout-media_left` or `.layout-media_top` returns **nothing** — only `.layout-visual_choices_three` has layout-specific rules (~line 288). `media_left_choices_right` and `media_top_choices_bottom` are dead code paths: they change the class name but not a single layout rule reads that class, so every non-`visual_choices_three` question silently falls back to the single generic `.game-stage` column with `.hero-image` fixed at `width:800px;height:284px` (~line 225). This is the single biggest reason the video reads as "flat" and the image boxes read as "too small" compared to the reference genre convention of a large, near-full-height photo bleeding along one side of the frame. |

Confirmed by direct pixel measurement against extracted frames. |
| 4 | Narration reads as slow / dragging, never energetic, no audible acceleration on exciting beats | `apps/server/src/quiz/audio/voiceSynthesis.ts` `quizVoiceTempo()` (~line 55–62) | Every role returns an `atempo` value **below 1.0**: question/choice/intro/outro `0.84`, reveal `0.86`, explanation/fun_fact `0.82`, thinking_prompt `0.9`. Every single narration segment in the pipeline is deliberately slowed relative to the raw TTS output, with no role reaching or exceeding natural speed. This is a fully quantified, reproducible cause of "chậm rề rà" pacing — it is not a subjective impression, it is a config value. |
| 5 | Hero images (Mars, animals, oceans, etc.) read as flatter / less dimensional than the answer-option images | `apps/server/src/quiz/assets/assetPlanner.ts` (~line 9–22) vs (~line 23–55) | `hero_question_image` assets are planned with only `style: "cute_illustration"` and no `consistency_group_id`, so `promptCompiler.ts`'s `groupContract` (which carries `rendering_medium: "polished 3D clay-like illustration"`, `lighting`, `edge_treatment` with rim light, `detail_level`, `face_policy`) is **empty** for hero images (`consistencyGroup` is `undefined`, see `compileQuizAssetPrompt`). Only `answer_option` assets inside a `visual-answer-set` consistency group get that dimensional-lighting treatment. Hero images fall back to only the generic Style Bible line ("bright, friendly, high saturation, medium-high contrast, clean lighting, large identifiable subject, simple composition"), which under-specifies rendering medium/depth and also never states a face policy, so results are inconsistent (e.g. a smiling-face Mars in one render, a plain photographic-style ocean in another). |

# PHASE 1 — Fix the Thinking Bar marker distortion (bug #1)

Decouple the marker's shape from the fill's scale animation. The fill (`.timer-progress`)
and the marker (`.timer-marker`) must be siblings, not parent/child, so the marker's own
`width/height/border-radius` are never inside a scaled coordinate system.

Concretely:

- Keep `.timer-progress` as the colored fill bar only (no child element inside it). It can
  keep `transform-origin:left` + the `quiz-timer-drain` `scaleX` animation.
- Move `.timer-marker` to be a **sibling** of `.timer-progress` inside `.thinking-track`,
  absolutely positioned with `left` (or a `translateX` on a wrapper that is *not* the scaled
  element) animated from `100%` → `0%` over the same `var(--timer-duration)` / `--clip-start`
  window, using a **new** keyframe (e.g. `quiz-timer-marker-slide`) that animates `left`
  (or `transform: translateX(...)`) — never `scaleX` — so its own `border-radius:50%` circle
  is never non-uniformly scaled.
- The fill and the marker must stay visually synchronized (marker sits exactly at the fill's
  trailing edge at every frame) — verify this by sampling both animations at matching
  progress values (0%, 25%, 50%, 75%, 100%) and asserting the marker's `left`/`translateX`
  matches the fill's scaled width at each sample, the same way the V3 fix synchronized fill
  and marker under one clock (see `docs/candy-arcade-v3-root-cause.md`, "Progress jump" row) —
  just without nesting them.
- Do not reintroduce the countdown-tick-restart bug that V3 fixed: this must remain **one**
  persistent timer clip per question, not one clip per tick.

Acceptance: render a question's full thinking-phase clip, extract ≥8 frames evenly spaced
across the countdown, and measure the marker's on-screen bounding box in each frame. Its
width/height ratio must stay within a tight tolerance (e.g. 0.92–1.08) of a perfect circle at
every sampled frame, including the final frames of the countdown (this is exactly where the
current bug is worst).

# PHASE 2 — Implement real media-left / media-top layouts with large, bleeding hero art

Bring `media_left_choices_right` and `media_top_choices_bottom` to life instead of leaving
them as unused class names. Target proportions, in the spirit of the large-photo /
answers-beside-it convention common to this quiz-video genre (do not copy any specific
video's exact pixel layout or branding — implement the general convention):

- **`media_left_choices_right`**: two-column `.game-stage`. Left column: the hero image,
  full-bleeding vertically (roughly 85–95% of the available stage height, not a small boxed
  card), rounded corners consistent with the existing card language. Right column: question
  title (if it doesn't already sit above the whole stage) and the answer list stacked
  vertically, each answer still using the existing letter-badge pill style. Reserve a
  visually generous share of the 1920px stage width for the image column (roughly 45–55%) so
  it reads as a genuine hero, not a thumbnail.
- **`media_top_choices_bottom`**: single column, but the hero image should be substantially
  larger than the current `800×284` box — target something closer to filling the width of
  `.game-stage` at a taller aspect ratio (e.g. 16:9 or 4:3 at ~1500–1600px wide), leaving
  clear room below for the answer grid and Thinking Bar without crowding.
- Update `resolveLayout()` callers / the CSS selectors so `layout-media_left_choices_right`
  and `layout-media_top_choices_bottom` each have real, distinct grid rules — mirror how
  `.layout-visual_choices_three` already gets its own rules, and give each layout its own
  entrance-animation timing the same way that layout does (~line 288).
- Increase the base `.game-stage > .hero-image` size (currently `800px × 284px`, ~line 225)
  as the fallback/default, but the primary fix is making the two layout-specific rules above
  actually govern sizing when those layouts are selected.
- Re-run `assessQuizVisualLayout` mentally against every archetype
  (`text_multiple_choice`, `illustrated_multiple_choice`, `visual_multiple_choice`,
  `true_false`, `image_guess`, `odd_one_out`) to confirm every one still resolves to a layout
  with working CSS after this change — none should silently fall through to a
  layout class with no matching rule again.

Acceptance: for a sample question in each layout, measure the hero image element's rendered
area as a percentage of the 1920×1080 frame. `media_left_choices_right` and
`media_top_choices_bottom` should both render the hero image at a meaningfully larger area
than the current baseline (document the before/after percentage in your report — this is the
core visual complaint from the source review, so the improvement must be measurable, not
just claimed).

# PHASE 4 — Fix narration pacing

In `voiceSynthesis.ts`, `quizVoiceTempo()`: move every role's baseline to natural speed or
faster. As a starting point (tune by ear against measured segment durations, and keep
`docs/candy-arcade-v3-root-cause.md`'s constraint in mind — only `atempo` and the existing
Chatterbox `exaggeration`/`cfg_weight` fields are available, no other provider parameter):

- `question` / `choice`: raise from `0.84` toward roughly `1.05–1.15` — these currently read
  slowest and are the most repetitive line-type across the video.
- `reveal`: raise from `0.86` toward roughly `1.05–1.1`, but keep it distinguishable in
  *delivery* (the existing `exaggeration: .8` / `cfg_weight: .38` performance config) rather
  than relying on slowness for weight.
- `explanation` / `fun_fact`: these can stay closer to natural pace (~`0.95–1.0`) since they
  are the "teaching" beat, but should not be slower than natural.
- `thinking_prompt`: keep close to natural pace (~`1.0`); this is meant to feel like a quick
  nudge, not a lingering line.
- `intro` / `outro`: raise toward `1.0–1.1` to open/close with energy.

After changing tempos, re-check `apps/server/src/quiz/timeline/timingPolicy.ts` and the
preflight minimum-thinking-time gate — durations will shrink, so confirm
`minimum_thinking_seconds` / `maximum_thinking_seconds` per age band and the timeline
compiler's use of measured durations still produce a comfortable, non-rushed pacing for the
target age band, not just a technically-passing one. Re-run
`apps/server/test/quizPacing.test.ts` and `audioDiagnostics.test.ts`.

Separately, review `voicePlan.ts`'s `voiceCopy()` phrase banks (`thinking`, `reveal`,
`outro`) for opportunities to add more varied, higher-energy phrasing (more exclamations,
direct-address hooks like "Ready?" / "Here we go!" equivalents) consistent with the existing
delivery-tag system (`emphasis`, `playful`, `warm`, `question_end`), without changing
canonical question/answer/explanation text. This is a content tweak, not a new system — reuse
`performancePhrases()`.

Acceptance: report measured total narration duration before/after for a fixed sample episode,
per-role average words-per-second before/after, and confirm
`apps/server/test/audioDiagnostics.test.ts` and `quizPacing.test.ts` still pass (update their
expected-value fixtures if they hard-code the old tempo numbers — check first).

# PHASE 6 — Game-feel juice, read-along highlight, subtle zoom, and a streak cue

This phase targets kid-appeal specifically, beyond raw image size/pacing. All of it is
additive and lower-risk than Phases 1–4 (no timing/QA-gate interaction), so it can be done
in parallel with, or immediately after, Phases 1–4.

Not in scope for this pass: a recurring reacting mascot character. `apps/server/src/quiz/render/buildComposition.ts`'s
legacy `v2Css()` (the pre-Candy-Arcade V1 composition, not on the current render path) already
contains a complete CSS mascot — `.mascot`, with `mascot-wave`, `mascot-thinking`,
`mascot-celebrate`, `mascot-point`, `mascot-encourage` state classes — that the current Candy
Arcade composition dropped in favor of a small intro-only `brand-mascot` badge. This is a real
opportunity (the asset already exists, low implementation risk) but the operator wants to
think it through separately before committing to a character design/personality. Do not port
or implement any mascot character in this pass. Leave a short note in your Phase 8 report
pointing back at this paragraph so it isn't lost, but do not act on it.

What IS in scope:

- **Add squash-and-stretch / overshoot "juice" to the reveal moment specifically.** The
  correct-answer reveal already has `correct-card-reveal`, `stamp-pop`, and `reward-fx` star
  bursts — good bones. Push the reveal beat harder than any other moment on screen: a brief
  overshoot scale-bounce on the correct card (beyond the current `scale(1.03)` settle), a
  screen-safe "impact" flash or radial burst behind the correct card, and denser/faster
  reward particles than the current 5–7 stars for the non-final reveals (currently only the
  final question gets `reward-big`; consider giving every correct reveal a slightly bigger
  moment than it has now, since this is the single emotional payoff beat per question).
- **Highlight the key noun in each question/answer.** Wrap the semantically important word or
  phrase in the question (subject: "Red Planet", "penguin", etc.) in a colored/bold inline
  span so it visually pops against the rest of the question text — this both draws a young
  reader's eye and reinforces word-recognition for kids who are still learning to read along.
  This needs a data source: either have the Director plan annotate which substring is the
  keyword, or derive it deterministically from `question.visual_opportunity` matching against
  the question text. Do not guess/highlight the wrong word — fall back to no highlight rather
  than a wrong one.
- **Give the hero image a very slow, continuous zoom (Ken Burns).** On top of the existing
  `hero-float`, add a slow, deterministic `scale(1.0 → 1.06)` drift over the image's full
  on-screen duration (question → choices → think → reveal → explain), so the frame never
  feels perfectly static even during longer thinking windows. Keep it subtle enough not to
  compete with the float, and make sure it doesn't reveal answer-relevant crops of visual-
  choice images (respect the existing fairness/consistency-group constraints from
  `visualFairnessIssues`).
- **Consider a light "streak" cue, not a full score system.** A full running score UI would
  need interactivity this pipeline doesn't have (it's a passive video, not a live quiz), so
  don't build a scoring system. But a small rhetorical touch — e.g. a brief "🔥" or sparkle
  accent on the episode-progress pill after a run of reveals, or simply making the
  `episode-progress` counter itself pop/bounce on increment — can add a game-like feedback
  loop cheaply without implying real interactivity.

Acceptance: extract frames at the start/mid/end of a `phase-reveal` clip before/after, and
confirm the reveal moment reads noticeably more energetic in a side-by-side still comparison,
the keyword highlight lands on the correct word for a sample of questions (spot-check at
least 5), and the Ken Burns drift is present but does not exceed the fairness/consistency
constraints for visual-choice questions.
